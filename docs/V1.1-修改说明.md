版本：v1.1（软件版本 1.1.0）  
设计依据：[园区 AI 中枢交接文档](design-handoff-source.md)  
后续项目目录：`C:\auto work\bailuwan-ai-hub-v1.1`

## 本次范围与取舍

本次按用户“对系统做适当程度修改并交付 v1.1”的要求实施。在现有数字孪生、业务 API、SQLite 与设备模拟器上增加统一资源与任务中枢，优先解决资源选择、计划解释、风险确认和执行反馈的共用问题。保留 v1.0 的设备、巡检、消防、配送、OA、考勤和人工接管能力。

交接文档中的“先检查与计划、等待批准后开发”作为团队建议流程记录；本次直接实施依据是用户在当前任务中明确提出的修改与版本交付要求。以下先记录现状对照和增量计划，再记录实际修改与验证，便于团队复核。

本仓库没有 UE 工程，现有三维端是 Three.js。本次维持该可运行三维端，提供统一孪生快照与更新接口供未来 UE 客户端接入；不将网页渲染器改名为 UE，也不宣称已完成 UE 工程。

v1.0 真正可操作的基础是设备控制回执、安防/消防状态机、OA 与配送、巡检和人工接管。自然语言工具是规则模拟；视频证据、设备遥测和任务运动也是明确的模拟数据。最影响复用性的结构问题是缺少共同的“目标—资源—计划—执行—反馈”对象，而不是缺少另一套三维动画。

新数据库初始化包含原 102 台设备、6 个会议空间、3 个职能岗位和 8 个园区区域。资源状态按设备、旧业务任务、当前预订和中枢任务实时派生，不将状态重复保存成另一份设备清单。资源选择为能力筛选后结合距离、电量、容量评分的确定性策略，候选理由会返回界面。

任务计划不会直接占用或控制资源。执行时重新匹配并校验；配送先生成关联订单和 OA，批准后才能调度；运输进度来自原模拟器；到达后还需人工反馈，才签收归档。巡检复用原机器人任务。会议“完成”表示空间预订及模拟通知记录完成，不表示会议已经召开。

火情事件按输入建筑与楼层定位；设备联动仍复用原建筑级消防预案，覆盖该建筑照明与空调，不能理解为仅控制告警楼层。高风险确认后等待所有设备回执，失败或超时会将中枢任务标为失败并保留未闭环事件。跌倒协助只匹配职能岗位、记录通知并等待人工反馈，不虚构到场、诊断或救治结果。

## 验收记录

本次执行 `npm run build` 通过；`npm test` 共 **23 项通过，0 项失败**，一次实测约 6.28 秒，包含原 15 项回归测试与 8 项中枢测试。测试使用隔离数据库，不修改正在运行的 v1.0 数据。

| 新增测试范围 | 已验证行为 |
| --- | --- |
| 资源与访问范围 | 空间、岗位和语义能力存在；低电量/离线即时反映；普通用户不能读取他人目标与通知；孪生快照返回统一状态 |
| 自然语言配送 | 从 B03 到 B06、2 公斤与收件岗位被解析；计划幂等；OA 门禁、模拟运输、人工交接、签收归档与任务状态一致 |
| 资源失效 | 计划后设备变为不可用，执行时返回带候选理由的阻塞任务，不创建虚假运输 |
| 指定区域巡检 | 使用共享能力匹配、暂停/继续和原模拟器进度，最终业务与中枢状态一致 |
| 会议安排 | 执行时重查人数/时段冲突；同槽第二个任务被阻塞；本人取消后可重规划并预订 |
| 火情处置 | B06 动态事件拒绝后没有设备指令且告警仍保留；B04 确认后等待回执，人工归档后传感器恢复 |
| 跌倒协助 | 指定位置匹配岗位、确认后等待人工反馈、无设备指令；模拟通知有明确通道标识；人工结案归档 |
| 接管和失败 | 接管阻断新中枢执行；设备失败向中枢传播，任务不伪报完成；审计链校验通过 |

浏览器交互、目标目录复制与目标目录启动尚在最终检查阶段，以上 API 测试不替代这些验收。发布前须将实际浏览器与启动结果追加到本节。

## 明确边界与后续方向

- 自然语言理解采用可解释规则与结构化输入补充，未接入本地大模型；无法理解的目标应返回可操作错误。
- 会议通知与事件通知是系统内模拟通知，不代表短信、电话、企业微信或真实救援单位已收到消息。
- 跌倒案例只协调帮助，不提供诊断，不把模拟人员指派等同于实际到场或救治完成。
- UE 工程、真实模型资产、真实设备协议与人员身份系统仍需团队提供并单独接入。
- 本次不扩展成通用企业 BPMN 编排器、实时多机器人路径避碰、真实消防安全控制或生产认证系统。
- 后续应在统一资源能力和任务接口上继续增加适配器、任务类型与策略，避免在三维客户端重写业务流程。
